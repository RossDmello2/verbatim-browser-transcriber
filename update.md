# Verbatim Reconstruction Specification

This file is the single source of truth for recreating the current app exactly as it behaves today.

The app is a client-only browser workspace named `Verbatim`, with an embedded assistant named `Verba`. It is not a basic recorder. It is a full transcription workstation that combines:

- live browser speech recognition
- high-accuracy recorded transcription through AI APIs
- audio and video file transcription
- multilingual preserve-original transcription
- translate-to-English file mode
- live segment translation with sentiment and tone
- transcript cleanup and correction tools
- workspace autosave, restore, backup, import, and cache
- AI output generation
- long-term imported memory packs
- a multimodal assistant with chat history, voice input, and file attachments

If another LLM rebuilds the app from this file, it must preserve the current architecture, feature set, UI relationships, storage model, and behavior described below.

## 1. File Structure

The project currently contains only these functional app files:

- `index.html`
- `style.css`
- `script.js`

No backend exists in this repo. All AI traffic is sent directly from the browser to external APIs using `fetch`.

## 2. Overall Architecture

### 2.1 Runtime model

- `index.html` is only a shell.
- The body contains:
  - `#toastContainer`
  - `.page#page`
  - `#mainContent`
- `script.js` runs on load.
- It feature-detects browser capabilities first.
- If the browser is too limited, it renders a "browser support is too limited" screen.
- Otherwise it calls `buildApp()`.

### 2.2 Important consequence

The real application DOM is not written directly in `index.html`. The entire interface is injected by `script.js` using `mainContent.innerHTML`.

This means a faithful rebuild must preserve the same pattern:

1. Minimal HTML shell.
2. Full UI generated by JavaScript.
3. CSS styles the generated UI.

## 9. Modes

There are 3 top-level modes:

- `realtime`
- `quality`
- `file`

### 9.1 Live mode

Purpose:

- instant browser speech recognition
- interim text as the user speaks
- finalized segments committed over time

Key traits:

- only works with microphone
- uses `SpeechRecognition`
- maintains a backup `MediaRecorder` audio buffer in the background
- can trigger fallback API transcription if live reliability degrades

### 9.2 Quality mode

Purpose:

- record audio first
- then send audio to AI transcription for better accuracy

Key traits:

- requires API key
- can use microphone, browser-tab audio, or screen/system audio depending on browser support
- uses `MediaRecorder`
- when stopped, the captured blob is decoded, processed, and transcribed

### 9.3 File mode

Purpose:

- upload local audio or video
- preprocess locally
- transcribe or translate through AI APIs

Key traits:

- accepts media files up to 500MB
- supports preserve-original-language mode
- supports translate-everything-to-English mode
- shows a persistent audio player in the transcript header
- supports transcript caching by file hash and options

## 18. Transcription Pipelines

### 18.1 Live mode pipeline

1. Start `SpeechRecognition`.
2. Start timer and audio visualizer.
3. Start backup live audio buffer recorder.
4. Show interim text while user speaks.
5. Score alternatives and confidence.
6. Schedule finalized segments for commit.
7. Apply smart punctuation if enabled.
8. Maintain live health score.
9. If live quality degrades badly and API keys exist:
   - stop live backup buffer
   - run high-accuracy fallback API transcription
   - insert fallback result as a segment
   - restart live backup buffer

### 18.2 Quality mode pipeline

1. Acquire chosen capture stream.
2. Start `MediaRecorder`.
3. Record chunks.
4. On stop, build blob.
5. Decode locally when possible.
6. Analyze audio.
7. Preprocess:
   - optional normalization
   - high-pass filter at 80Hz
   - compression
   - gain normalization
8. Resample to 16kHz mono.
9. Convert to WAV.
10. Chunk at roughly 24MB max chunk size.
11. Transcribe each chunk.
12. Merge results and render transcript.

### 18.3 File mode pipeline

1. Read file into ArrayBuffer.
2. Hash with SHA-256.
3. Build transcript cache key from:
   - file hash
   - provider
   - task type
   - language
   - model
   - normalize/raw flag
4. If cache exists and cache use is enabled:
   - reuse cached result
5. Else attempt local decode.
6. Analyze audio.
7. Preprocess and normalize if enabled.
8. Resample to 16kHz.
9. Convert to WAV.
10. Chunk to <= 24MB pieces.
11. Transcribe or translate chunk-by-chunk.
12. Save partial progress during chunking for resume support.
13. Merge chunk results.
14. Optionally trigger adaptive retry for difficult audio.
15. Run multilingual repair when preserve-original mode applies.
16. Cache final result.
17. Display transcript and segments.

### 18.4 Direct upload fallback

If local decode fails and file is <= 24MB:

- upload original media blob directly to speech API

If local decode fails and file is > 24MB:

- error

## 20. Multilingual Repair System

This is a defining feature and must be preserved.

### 20.1 Why it exists

Whisper-style output can degrade on mixed Marathi/Hindi/English audio:

- English-only drift
- missed Devanagari
- garbled segments
- repeated filler fragments
- low-confidence mixed-language errors

### 20.2 Trigger conditions

Multilingual repair is considered when:

- preserve-original mode is active
- mixed language spread exists
- script mismatch exists
- enough suspicious segments exist
- multiple low-confidence/garbled segments exist

### 20.3 Repair behavior

- suspicious segments are batched
- batches are sent to chat model
- system prompt instructs:
  - preserve original languages
  - keep Marathi/Hindi in Devanagari whenever recoverable
  - keep English technical terms in English
  - preserve meaning and timestamps
  - optionally drop noise-only segments
- returned JSON patches the affected segments
